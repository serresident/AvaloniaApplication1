# 1. АРХИТЕКТУРА

## 1.1 Clean Architecture

Приложение должно иметь четкое разделение ответственности.

Рекомендуемая структура:

```text
Solution
│
├── Domain
│   ├── Entities
│   ├── ValueObjects
│   ├── Interfaces
│   └── DomainServices
│
├── Application
│   ├── UseCases
│   ├── DTO
│   ├── Interfaces
│   ├── Services
│   └── Validators
│
├── Infrastructure
│   ├── Network
│   ├── Persistence
│   ├── Protocols
│   ├── Configuration
│   └── Implementations
│
├── Presentation
│   ├── Views
│   ├── ViewModels
│   ├── Controls
│   └── Themes
│
└── Tests
```

Правило зависимостей:

```text
Presentation
      ↓
Application
      ↓
Domain

Infrastructure
      ↓
Application / Domain interfaces
```

### Запрещено

* Domain не должен зависеть от UI.
* Domain не должен зависеть от Avalonia.
* Domain не должен зависеть от Infrastructure.
* Application не должен зависеть от конкретных сетевых библиотек.
* ViewModel не должна напрямую работать с БД, MQTT, Modbus, HTTP или файловой системой.
* Protocol Driver не должен знать о ViewModel.
* View не должна содержать бизнес-логику.

# 2. SOLID И ОТВЕТСТВЕННОСТЬ КЛАССОВ

## 2.1 Single Responsibility Principle

Один класс — одна ответственность.

Запрещены классы, которые одновременно:

* работают с сетью;
* управляют UI;
* хранят состояние;
* парсят данные;
* пишут логи;
* работают с конфигурацией.

Если класс начинает выполнять несколько независимых задач — он должен быть декомпозирован.

### Практическое ограничение

Если класс:

* превышает примерно 300–400 строк;
* имеет более 5–7 зависимостей;
* содержит несколько независимых областей логики;

необходимо рассмотреть декомпозицию.

Количество строк само по себе не является абсолютным критерием. Главный критерий — количество ответственностей.

---

## 2.2 Open-Closed Principle

Система должна быть открыта для расширения и закрыта для изменения.

Запрещается создавать большие конструкции:

```csharp
switch (type)
{
    case ...
    case ...
    case ...
    case ...
}
```

для выбора реализаций, драйверов или стратегий.

Предпочитать:

* Strategy;
* Factory;
* Abstract Factory;
* Polymorphism;
* DI registration;
* keyed services или отдельные фабрики, если это оправдано.

Пример:

```csharp
public interface IProtocolDriver
{
    ProtocolType ProtocolType { get; }

    Task ConnectAsync(
        CancellationToken cancellationToken);

    IObservable<ProtocolMessage> Messages { get; }
}
```

Новые протоколы должны добавляться через новую реализацию интерфейса, а не через изменение центрального `switch`.

# 3. DEPENDENCY INJECTION

## 3.1 Constructor Injection

Все зависимости передаются через конструктор.

Правильно:

```csharp
public DeviceService(
    IDeviceRepository repository,
    IProtocolDriverFactory driverFactory,
    ILogger<DeviceService> logger)
{
}
```

Неправильно:

```csharp
var client = new MqttClient();
```

внутри бизнес-сервиса.

---

## 3.2 Разрешенные случаи использования new

Оператор `new` допустим для:

* DTO;
* Entity;
* Value Object;
* локальных структур;
* коллекций;
* исключений;
* объектов, которые являются частью внутреннего алгоритма и не имеют внешней зависимости.

Необходимо избегать:

```csharp
new HttpClient()
new MqttClient()
new Repository()
new Service()
new ViewModel()
```

внутри бизнес-логики.

---

## 3.3 Service Locator запрещен

Запрещено:

```csharp
serviceProvider.GetRequiredService<T>();
```

использовать как скрытую замену Dependency Injection внутри бизнес-кода.

`IServiceProvider` не должен передаваться в обычные сервисы без архитектурной необходимости.

---

# 4. DOMAIN И APPLICATION LAYER

## 4.1 Domain должен быть независимым

Domain Layer содержит:

* бизнес-сущности;
* Value Objects;
* бизнес-правила;
* доменные интерфейсы;
* доменные события.

Domain не должен знать:

* Avalonia;
* ReactiveUI;
* MQTT;
* Modbus;
* Entity Framework;
* HTTP;
* конкретную БД.

---

## 4.2 DTO

Внешние данные передаются через DTO.

Например:

```csharp
public sealed record DeviceTelemetryDto(
    string DeviceId,
    DateTimeOffset Timestamp,
    double Temperature,
    double Pressure);
```

DTO не должны содержать:

* UI-логику;
* сетевую логику;
* бизнес-процессы.

---

# 5. RX.NET И ПОТОКИ ДАННЫХ

## 5.1 Высокочастотные данные

Для телеметрии, сетевых сообщений, потоковых данных и состояния устройств использовать:

```csharp
IObservable<T>
```

Запрещается использовать обычные `event` для маршрутизации высокочастотных потоков данных.

---

## 5.2 Стандартный поток данных

Рекомендуемая схема:

```text
Protocol Driver
       ↓
IObservable<DTO>
       ↓
Application Service
       ↓
State / Stream
       ↓
ViewModel
       ↓
Avalonia UI
```

UI не должен получать сырые сетевые сообщения напрямую.

---

## 5.3 Защита UI-потока

Любая подписка, изменяющая состояние ViewModel, должна переключаться на UI Scheduler:

```csharp
_subscription = source
    .ObserveOn(RxApp.MainThreadScheduler)
    .Subscribe(UpdateState);
```

Запрещено обновлять UI-bound свойства из фонового потока.

---

## 5.4 Защита от перегрузки UI

Высокочастотные данные должны ограничиваться.

Использовать:

```csharp
.Sample(...)
.Throttle(...)
.Buffer(...)
.DistinctUntilChanged()
```

Обычный рекомендуемый интервал обновления UI:

```text
50–100 мс
```

или реже, если более высокая частота не требуется.

Не отправлять каждое сетевое сообщение непосредственно в UI.

---

# 6. IDisposable И MEMORY LEAKS

## 6.1 Все подписки должны освобождаться

Каждый класс, который подписывается на:

* `IObservable`;
* события;
* таймеры;
* внешние ресурсы;

обязан корректно освобождать ресурсы.

Использовать:

```csharp
private readonly CompositeDisposable _disposables = new();
```

Подписки:

```csharp
source
    .Subscribe(...)
    .DisposeWith(_disposables);
```

Освобождение:

```csharp
public void Dispose()
{
    _disposables.Dispose();
}
```

---

## 6.2 Висячие подписки запрещены

Запрещено:

```csharp
observable.Subscribe(...)
```

без управления жизненным циклом подписки.

Особенно опасны:

* singleton-сервисы;
* ViewModel;
* фоновые сервисы;
* страницы, создаваемые и уничтожаемые многократно.

---

## 6.3 Lifetime ViewModel

Жизненный цикл подписок ViewModel должен быть явно определен.

При уничтожении ViewModel:

* отменяются операции;
* освобождаются Rx-подписки;
* освобождаются ресурсы.

---

# 7. AVALONIA UI

## 7.1 MVVM обязателен

View:

```text
Отображает UI
```

ViewModel:

```text
Управляет UI State
```

Application/Domain:

```text
Содержит бизнес-логику
```

---

## 7.2 Compiled Bindings обязательны

Во всех `.axaml` файлах необходимо использовать compiled bindings.

Пример:

```xml
<UserControl
    x:Class="MyApp.Views.MainView"
    x:DataType="vm:MainViewModel"
    CompiledBindings="True">
```

Ошибки биндингов должны обнаруживаться максимально рано.

---

## 7.3 Code-behind

В `.axaml.cs` допускается только:

* `InitializeComponent()`;
* логика нативных контролов;
* специфичная UI/рендеринг логика;
* platform-specific UI integration.

Запрещено:

* изменять бизнес-состояние;
* выполнять бизнес-операции;
* обращаться к репозиториям;
* работать с сетью;
* вызывать Use Cases напрямую.

Неправильно:

```csharp
private async void Button_Click(...)
{
    await _mqttClient.ConnectAsync();
}
```

# 8. VIEWMODEL

## 8.1 ViewModel не должна быть God Object

ViewModel отвечает только за:

* UI State;
* UI Commands;
* преобразование Application Model в Presentation Model;
* подписку на необходимые UI-потоки.

ViewModel не должна:

* подключаться к MQTT напрямую;
* выполнять Modbus-команды напрямую;
* читать БД;
* парсить сетевые пакеты.

---

## 8.2 Commands

Для пользовательских действий использовать команды.

Асинхронные операции не должны блокировать UI.

Команда должна:

* корректно обрабатывать ошибки;
* поддерживать отмену при необходимости;
* предотвращать неконтролируемый параллельный запуск.

---

# 10. АСИНХРОННОСТЬ

## 10.1 Только async/await

Запрещено:

```csharp
.Result
.Wait()
.GetAwaiter().GetResult()
```

в UI и обычном асинхронном коде.

Это может привести к:

* deadlock;
* блокировке UI;
* thread starvation.

---

## 10.2 CancellationToken обязателен

Все потенциально длительные операции должны принимать:

```csharp
CancellationToken cancellationToken
```

Например:

```csharp
Task<DeviceDto> GetDeviceAsync(
    string id,
    CancellationToken cancellationToken);
```

Это относится к:

* HTTP;
* MQTT;
* Modbus;
* файловым операциям;
* БД;
* парсингу больших данных;
* вычислениям;
* reconnect loops.

---

## 10.3 CancellationToken нельзя игнорировать

Если метод принимает `CancellationToken`, он должен передаваться во все нижележащие операции, где это возможно.

---

# 11. СЕТЬ И ПРОТОКОЛЫ

## 11.1 Полная изоляция протоколов

Протоколы:

* MQTT;
* Modbus;
* HTTP;
* TCP;
* UDP;
* WebSocket;

не должны проникать в Presentation Layer.

UI не должен знать:

```text
MQTT Topic
Modbus Register
TCP Socket
Packet Format
```

---

## 11.2 Protocol Driver

Каждый драйвер отвечает за конкретный протокол.

Например:

```text
IProtocolDriver
├── MqttProtocolDriver
├── ModbusProtocolDriver
├── HttpProtocolDriver
└── TcpProtocolDriver
```

Драйвер преобразует protocol-specific данные в стандартные DTO.

---

## 11.3 Reconnection

Логика переподключения должна быть:

* изолированной;
* отменяемой;
* защищенной от бесконечного создания задач;
* логируемой.

Не использовать бесконтрольные:

```csharp
while (true)
{
}
```

без:

* `CancellationToken`;
* задержки;
* политики retry;
* обработки ошибок.

---

# 12. ОШИБКИ И ЛОГИРОВАНИЕ

## 12.1 Исключения нельзя скрывать

Запрещено:

```csharp
catch
{
}
```

или:

```csharp
catch (Exception)
{
}
```

без обработки.

---

## 12.2 Structured Logging

Использовать структурированное логирование.

Например:

```csharp
_logger.LogInformation(
    "Device {DeviceId} connected",
    deviceId);
```

Не использовать:

```csharp
_logger.LogInformation(
    $"Device {deviceId} connected");
```

если доступно структурированное логирование.

---

## 12.3 Уровни логирования

Использовать:

```text
Trace
Debug
Information
Warning
Error
Critical
```

Не логировать ожидаемые события как ошибки.

---

# 13. СОСТОЯНИЕ ПРИЛОЖЕНИЯ

## 13.1 Single Source of Truth

Каждое важное состояние должно иметь явный источник.

Запрещено одновременно хранить одно состояние:

* в View;
* ViewModel;
* Service;
* статической переменной.

---

## 13.2 Thread Safety

Общее состояние должно быть:

* immutable;
* синхронизированным;
* или обновляться через контролируемый поток.

Избегать неконтролируемого доступа к:

```csharp
List<T>
Dictionary<TKey, TValue>
```

из нескольких потоков.

---

# 14. NULLABILITY

В проекте должны быть включены nullable reference types.

Предпочитать:

```csharp
string?
```

вместо неявного предположения о возможном `null`.

Не использовать null как универсальный индикатор состояния.

При необходимости использовать:

* Result;
* Option-подход;
* явные State Objects.

---

# 15. ИММУТАБЕЛЬНОСТЬ

Предпочитать immutable объекты.

Особенно для:

* DTO;
* Configuration;
* Messages;
* Events;
* State.

Например:

```csharp
public sealed record DeviceState(
    string DeviceId,
    bool IsConnected,
    double Temperature);
```

# 17. ИМЕНА И ЧИТАЕМОСТЬ

Код должен быть самодокументируемым.

Плохо:

```csharp
var x = ...
var d = ...
```

Хорошо:

```csharp
var connectionState = ...
var telemetryMessage = ...
```

Метод должен описывать действие:

```csharp
ConnectAsync()
LoadDevicesAsync()
PublishTelemetryAsync()
```

Булевые свойства:

```csharp
IsConnected
HasError
CanExecute
```

# 20. ПРАВИЛА РЕФАКТОРИНГА

Если пользователь просит:

> Исправить конкретный метод

необходимо исправлять конкретный метод.

Запрещено переписывать весь проект без необходимости.

Если для правильного исправления требуется изменение нескольких модулей:

1. Кратко объяснить проблему.
2. Указать минимально необходимые изменения.
3. Не выполнять масштабный рефакторинг без явного согласования.

---

# 21. ФОРМАТ ОТВЕТА ПРИ НАПИСАНИИ КОДА

Перед кодом всегда кратко объяснять архитектурное решение.

Формат:

### Анализ

1–3 предложения:

* какую проблему решает решение;
* почему выбран этот подход;
* как соблюдаются архитектурные ограничения.

### Изменения

Кратко перечислить затронутые файлы или компоненты.

### Код

Показывать только необходимый код.

Не переписывать большие файлы, если пользователь просит исправить конкретный участок.

---

# 22. ЕСЛИ ЗАПРОС НАРУШАЕТ КОДЕКС

Если пользователь просит решение, которое нарушает архитектурные правила, нельзя механически выполнять запрос.

Необходимо:

1. Объяснить конкретное нарушение.
2. Кратко описать последствия.
3. Предложить архитектурно правильный вариант.
4. Реализовать альтернативу только в пределах согласованного изменения.

# 23. ПРАВИЛО МИНИМАЛЬНОГО ИЗМЕНЕНИЯ

Изменения должны быть минимальными, но достаточными.

При исправлении бага:

```text
Не менять архитектуру без необходимости.
Не переписывать соседние модули.
Не менять публичные API без необходимости.
Не выполнять "рефакторинг заодно".
```

Но если локальное исправление создаст:

* memory leak;
* deadlock;
* нарушение потокобезопасности;
* архитектурное нарушение;

необходимо сообщить об этом и предложить минимальное корректное изменение.
